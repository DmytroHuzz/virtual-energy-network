# Make the round trip work

**Goal:** route a TCP request and its reply between different subnets, before adding NAT.

There are three separate decisions:

1. The supervisor needs a route to LD1 and LD2 through the gateway.
2. The gateway must forward packets between its interfaces.
3. Each logical device needs a route back to the supervisor.

The gateway already has connected routes to both subnets. Inspect them, then enable IPv4 forwarding **inside the gateway namespace**:

```bash
ip -n lab-gw route show
ip netns exec lab-gw sysctl -w net.ipv4.ip_forward=1
```{{exec}}

`sysctl` changes a kernel networking setting here, not a Python application option. We are not changing the host namespace's forwarding setting.

Tell the supervisor where the operator subnet is:

```bash
ip -n lab-sup route add 10.20.0.0/24 via 192.0.2.1
ip -n lab-sup route get 10.20.0.11
```{{exec}}

**Expected:** a route through next hop `192.0.2.1`, using the supervisor's `eth0` and source `192.0.2.2`. The destination remains `10.20.0.11`; a next hop is where the packet goes next, not a replacement destination IP.

Add return routes in the logical devices:

```bash
ip -n lab-ld1 route add default via 10.20.0.1
ip -n lab-ld2 route add default via 10.20.0.1
ip -n lab-ld1 route get 192.0.2.2
```{{exec}}

A default route handles destinations without a more specific match. LD1 still uses its connected `/24` route to contact LD2 directly; it uses the gateway for `192.0.2.2`.

Now query from the supervisor:

```bash
cd /root/energy-lab
bash lab.sh status lab-sup 10.20.0.11
bash lab.sh status lab-sup 10.20.0.12
```{{exec}}

**Expected:** responses named `LD1` and `LD2`. This proves the TCP round trip, not merely that a route exists. The logical devices listen on their operator addresses at TCP port 10000; the gateway forwards packets without running their Python server.

Trace the request in words:

```text
supervisor 192.0.2.2 -> next hop 192.0.2.1
gateway -> connected operator subnet -> LD1 10.20.0.11
LD1 -> default next hop 10.20.0.1
gateway -> connected WAN subnet -> supervisor 192.0.2.2
```

For a given packet, routing does not translate the IP source or destination; a reply naturally reverses the endpoints. The router replaces Ethernet headers when sending the packet onto another link. NAT is not necessary for this topology while both directions have routes.

Run the supervisor program against both devices using its address list:

```bash
printf '10.20.0.11\n10.20.0.12\n' > logical_devices.conf
ip netns exec lab-sup python3 supervisor.py
```{{exec}}

`supervisor.py` sends `GET` plus a newline and reads a newline-delimited JSON response. The configuration file is shared through the filesystem; the process's network namespace determines which routes its socket uses.

Click **Check** to verify forwarding and actual responses over both routed paths.
