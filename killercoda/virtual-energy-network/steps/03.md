# A measurement becomes an alarm

LD1 needs an operator interface because the program also publishes IP multicast and serves TCP status. For now give it an unconnected veth pair. In the next step you will connect that cable to the operator LAN.

```bash
ip link add op1-p type veth peer name op1-n
ip link set op1-n netns lab-ld1
ip -n lab-ld1 link set op1-n name eth1
ip -n lab-ld1 addr add 10.20.0.11/24 dev eth1
ip -n lab-ld1 link set eth1 up
ip link set op1-p up
bash lab.sh start 1
```{{exec}}

`lab.sh start` only launches your programs and records their PIDs/logs. It does not build the network. The sensor reads `run/voltage1` every second. LD1 compares each measurement with threshold **10** and sends `LOCAL_ON` or `LOCAL_OFF`. The LED changes its in-memory state when it receives those commands.

Inspect the traffic at the LED. This capture stops after six frames:

```bash
ip netns exec lab-led1 timeout 8 tcpdump -l -eni eth0 -A -c 6 'ether proto 0x88b5'
```{{exec}}

**Predict:** what changes if voltage rises from 5 to 15? What happens at exactly 10?

```bash
bash lab.sh voltage 1 15
sleep 2
tail -n 4 run/led1.log
bash lab.sh status lab-ld1 10.20.0.11
```{{exec}}

You should see `Turning LED on LED1` and `alerted_local: True`. Equality also triggers the alarm (`>= 10`). The sensor LAN still has no IPv4 addresses.

Clear the alarm, inspect the result, then leave bay 1 high for the checkpoint:

```bash
bash lab.sh voltage 1 5
sleep 2
tail -n 2 run/led1.log
bash lab.sh voltage 1 15
```{{exec}}

The device receives sensor values and alarm commands on the same Ethernet segment; it ignores nonnumeric payloads. This matters because a raw socket can see other message types on that LAN.
