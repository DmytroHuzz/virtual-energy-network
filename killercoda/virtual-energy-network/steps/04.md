# Run software inside the network you built

**Goal:** connect a change in application input to an observable Ethernet frame and LED state.

The first bay uses three programs:

| Program | Network namespace | Job |
|---|---|---|
| `sensor.py` | `lab-s1` | Read `run/voltage1` and publish an integer each second |
| `logical_device.py` | `lab-ld1` | Compare the measurement with threshold 10 and publish an alarm command |
| `alert_led.py` | `lab-led1` | Listen for the command and log its LED state |

## Prepare LD1's second interface

The supplied logical-device program expects a sensor interface (`eth0`) and an operator interface (`eth1`). Prepare its second cable now. Its host end stays unattached until lesson 6; it is not another port on `br-s1`.

```bash
cd /root/energy-lab
ip link add op1-p type veth peer name op1-n
ip link set op1-n netns lab-ld1
ip -n lab-ld1 link set op1-n name eth1
ip -n lab-ld1 addr add 10.20.0.11/24 dev eth1
ip -n lab-ld1 link set eth1 up
ip link set op1-p up
```{{exec}}

The address belongs only to LD1's operator interface. The sensor-facing `eth0` still has no IPv4 address. A `/24` says that addresses sharing the first 24 bits are on that IP subnet; we will use `10.20.0.0/24` for the operator LAN.

Start the applications:

```bash
bash lab.sh start 1
sleep 2
tail -n 3 run/sensor1.log
tail -n 3 run/led1.log
```{{exec}}

`lab.sh` starts processes in the background and records their PIDs and logs. It does not create interfaces or bridges. For example, LD1 is launched with this command (shown for inspection; the helper has already run it):

```bash
ip netns exec lab-ld1 python3 -u /root/energy-lab/logical_device.py --name LD1 -s eth0 -o eth1 -a 10
```

`-s` and `-o` tell the application which local interface names to use; `-a 10` sets the threshold. `-u` makes Python flush log output promptly. An existing program can use namespace networking without implementing namespace APIs itself.

**Expected:** initial input 5 and `Turning LED off LED1`. The programs publish state repeatedly; repeated log lines are normal.

## Observe the frame before changing the input

```bash
ip netns exec lab-led1 timeout 8 tcpdump -l -eni eth0 -A -c 6 'ether proto 0x88b5'
```{{exec}}

The capture runs in the LED's network view. `-e` shows Ethernet headers, `-n` avoids name lookups, `-A` shows printable payload bytes, and `-c 6` stops after six frames. `timeout 8` stops it after eight seconds if insufficient traffic arrives.

Look for the measurement `5` and the separate `LOCAL_OFF` command. Binary Ethernet header bytes may look like punctuation in the ASCII view. These frames use multicast MAC `03:00:00:00:00:01` and experimental EtherType `0x88b5`, which identifies this lab's payload format. There is no IP packet or TCP/UDP port in these particular frames.

If the capture times out without those frames, check `run/sensor1.log` for application errors and inspect the sensor's two cable ends and `br-s1` membership. Capturing the right interface in the right namespace matters: this traffic belongs on the LED's `eth0`, not LD1's operator `eth1`.

## Trigger and clear an alarm

**Predict:** when you change the file to 15, which program decides whether to raise an alarm?

```bash
bash lab.sh voltage 1 15
sleep 2
tail -n 3 run/ld1.log
tail -n 3 run/led1.log
bash lab.sh status lab-ld1 10.20.0.11
```{{exec}}

**Expected:** LD1 reports its local alarm, and LED1 logs `Turning LED on LED1`. The sensor only sends measurements; LD1 owns the comparison. The status helper launches a TCP client inside LD1's own namespace, querying its operator address. This is a local application check, not yet a test of the future operator LAN.

Now clear the alarm:

```bash
bash lab.sh voltage 1 5
sleep 2
tail -n 2 run/led1.log
```{{exec}}

The LED should turn off. A value of exactly 10 also triggers the alarm because the comparison is `>= 10`. These values are demonstration numbers, not realistic voltage limits.

Leave bay 1 high for this and later checkpoints:

```bash
bash lab.sh voltage 1 15
sleep 2
```{{exec}}

**Before continuing:** you should be able to trace `file -> Sensor1 -> Ethernet measurement -> LD1 -> Ethernet command -> LED1`. LD1 ignores nonnumeric alarm commands when looking for measurements on that shared LAN.

Revisit the bridge now that it has forwarded real traffic:

```bash
ip -n lab-s1 link show eth0
bridge fdb show br br-s1
```{{exec}}

Find the sensor's `link/ether` MAC address in the FDB. **Expected:** a learned entry pointing to `s1-p`, the host end of that sensor's cable. This connects a device-side interface to the switch's view of where its frames come from. Permanent/local and multicast entries may also appear; they are not all learned endpoint addresses.
