# Publish stable gateway addresses with DNAT

**Goal:** follow a destination address translation and distinguish it from routing or an application proxy.

The supervisor can already reach private device addresses. Now suppose its configuration should use gateway-owned service addresses instead. We will map each of two WAN addresses to a logical device's TCP service:

| Supervisor connects to | Gateway forwards to |
|---|---|
| `192.0.2.10:10000` | `10.20.0.11:10000` (LD1) |
| `192.0.2.11:10000` | `10.20.0.12:10000` (LD2) |

This is one design choice for the exercise, not a requirement for every SCADA network. These WAN addresses still exist only inside the simulated network.

## Own the addresses, then translate the destinations

First assign both aliases to the gateway's WAN interface:

```bash
ip -n lab-gw addr add 192.0.2.10/24 dev eth1
ip -n lab-gw addr add 192.0.2.11/24 dev eth1
ip -n lab-gw -4 address show dev eth1
```{{exec}}

**Expected:** `eth1` owns `.1`, `.10` and `.11` on the WAN subnet. The gateway can now answer ARP for both aliases. Assigning an address does not create a TCP server on it.

Add LD1's translation:

```bash
ip netns exec lab-gw iptables -t nat -A PREROUTING \
  -i eth1 -d 192.0.2.10 -p tcp --dport 10000 \
  -j DNAT --to-destination 10.20.0.11:10000
```{{exec}}

The backslashes continue one shell command across lines. Read the rule from left to right:

| Part | Meaning |
|---|---|
| `ip netns exec lab-gw` | Change rules in the gateway's stack |
| `-t nat -A PREROUTING` | Append to the NAT chain that handles incoming packets before the routing decision |
| `-i eth1 -d 192.0.2.10` | Match packets arriving from the WAN for this alias |
| `-p tcp --dport 10000` | Match the status service |
| `-j DNAT --to-destination ...` | Rewrite the destination address and port |

Add the corresponding mapping for LD2:

```bash
ip netns exec lab-gw iptables -t nat -A PREROUTING \
  -i eth1 -d 192.0.2.11 -p tcp --dport 10000 \
  -j DNAT --to-destination 10.20.0.12:10000
```{{exec}}

After translation, the gateway's routing table selects `eth0` for the new destination in `10.20.0.0/24`. NAT has not replaced that routing decision. It also has not started a Python server on the gateway: the existing server in LD1 or LD2 answers.

## Make forwarding permission explicit

Address translation and firewall permission are separate. Allow packets belonging to established connections, allow WAN requests to the status service, then drop other forwarded traffic:

```bash
ip netns exec lab-gw iptables -A FORWARD \
  -m conntrack --ctstate ESTABLISHED,RELATED -j ACCEPT
ip netns exec lab-gw iptables -A FORWARD \
  -i eth1 -o eth0 -d 10.20.0.0/24 -p tcp --dport 10000 -j ACCEPT
ip netns exec lab-gw iptables -P FORWARD DROP
```{{exec}}

The `FORWARD` chain handles traffic passing through the gateway. The default policy applies when no rule accepts it. These rules are scoped to this lab's gateway namespace and illustrate one service; they are not a complete substation firewall policy.

Switch the supervisor configuration to the aliases and make fresh connections:

```bash
cd /root/energy-lab
printf '192.0.2.10\n192.0.2.11\n' > logical_devices.conf
ip netns exec lab-sup python3 supervisor.py
```{{exec}}

**Expected:** `.10` answers as LD1 and `.11` as LD2. The supervisor uses addresses in its own subnet, so it reaches the gateway aliases directly.

To make that distinction visible, remove only the supervisor's explicit route to the private subnet:

```bash
ip -n lab-sup route del 10.20.0.0/24 via 192.0.2.1
ip -n lab-sup route get 10.20.0.11 || echo 'Expected: no direct route to the private subnet'
ip netns exec lab-sup python3 supervisor.py
```{{exec}}

**Expected:** the private route lookup fails but both alias queries still work. Removing a client's route demonstrates address selection, not access control: a client given a suitable route could still send private-address requests allowed by the firewall.

## See both sides of the translation

Use the **+** near the terminal tabs to open a second terminal. The tabs share the filesystem. Before clicking the next block, select **Tab 1**; it will capture for 15 seconds:

```bash
ip netns exec lab-gw timeout 15 tcpdump -l -ni any 'tcp port 10000'
```{{exec}}

While it runs, select **Tab 2**, then run this block there:

```bash
cd /root/energy-lab
ip netns exec lab-sup python3 supervisor.py
```{{exec}}

Read the capture in Tab 1. For an LD1 request, look for:

| Observation point | Source IP | Destination IP |
|---|---|---|
| Arrives on gateway `eth1` | `192.0.2.2` | `192.0.2.10` |
| Leaves gateway `eth0` | `192.0.2.2` | `10.20.0.11` |
| Reply arrives on `eth0` | `10.20.0.11` | `192.0.2.2` |
| Reply leaves on `eth1` | `192.0.2.10` | `192.0.2.2` |

**Connection tracking** remembers the mapping and applies the reverse translation to replies. We do not need source NAT here: the logical devices already route replies to `192.0.2.2` through the gateway. Their return routes remain essential.

After the capture ends, inspect rule counters in either terminal:

```bash
ip netns exec lab-gw iptables -t nat -nvL PREROUTING
ip netns exec lab-gw iptables -nvL FORWARD
```{{exec}}

NAT chain counters count the initial packets that establish translations, not every packet in an established connection. Forwarding counters describe accepted forwarded packets.

Click **Check** to verify the two mappings and actual responses through them.
