# Break, observe, repair

A working diagram is only the beginning. Let's practice telling a link fault from an application fault.

## Fault 1: disconnect the local indicator

**Predict:** if LED1 loses its interface, will the supervisor still report LD1's alarm?

```bash
ip -n lab-led1 link set eth0 down
bash lab.sh voltage 1 5
sleep 2
bash lab.sh status lab-sup 192.0.2.10
tail -n 2 run/led1.log
```{{exec}}

LD1 should clear its local alarm while the LED log stops updating. Its raw socket can raise `OSError: Network is down`, terminating the small LED program. A successful SCADA-style status query does not prove that every field endpoint received a command.

Repair the link and restart the exited LED process. The helper leaves the still-running sensor and logical device alone. Repeated sensor publication brings the new LED process to the current state:

```bash
ip -n lab-led1 link set eth0 up
bash lab.sh start 1
sleep 2
tail -n 2 run/led1.log
bash lab.sh voltage 1 15
```{{exec}}

## Fault 2: remove the return path

Use a fresh connection so it cannot be confused with an existing TCP session:

```bash
ip -n lab-ld1 route del default
timeout 4 bash lab.sh status lab-sup 192.0.2.10 || echo 'Expected: no completed TCP response'
ip -n lab-ld1 route show
ip -n lab-gw route show
ip -n lab-ld1 route add default via 10.20.0.1
bash lab.sh status lab-sup 192.0.2.10
```{{exec}}

The gateway still knows where to forward the request. LD1 no longer knows how to reply to `192.0.2.2`. NAT does not replace routing.

## Your investigation checklist

1. Which namespace owns the failed process or interface?
2. Is the interface up and attached to the intended bridge?
3. Is the packet Ethernet-only, UDP multicast, or TCP unicast?
4. Where do request and response routes point?
5. Do packet captures and rule counters support your explanation?
